# loom-examples

Runnable examples for the [Loom](../loom) framework — one package per
`examples/<name>`, each demonstrating a usage pattern. Extracted from the main
`loom` repo to keep the framework/kernel repo lean; the catalogue of what each
example teaches lives in `loom/docs/examples.md` and `loom/AGENTS.md`.

## Setup

Loom is **not published** — examples consume it from a sibling `../loom` checkout
via `link:` (see [AGENTS.md](./AGENTS.md) for the full rationale). Lay the repos
out as siblings:

```
workspace/
├── loom/            # git clone the framework, then:  pnpm install && pnpm build
├── loom-plugins/    # 3P plugins — only `learning-router` needs this one
└── loom-examples/   # this repo, then:                pnpm install
```

```bash
# from loom-examples/, with ../loom installed + built:
pnpm install
pnpm -r build
pnpm -r test
pnpm --filter @loom/db-observability start   # run one end-to-end
```

## Examples

|---|---|
| `loom-starter` | Minimal flow + human-in-the-loop approval |
| `db-observability` | Transient hydration → durable repair (GenUI dashboards) |
| `blueprint-status` | Blueprint IR 2.0.0 on plain loom: widgets bind a value AND a status channel in the app's own projection, spans ride in grid cells, a degraded widget carries `source`, and the app's value contract sits in the terminal renderer's `check` seam — the canonical status matrix walked from real projection state (ADR 0097) |
| `experience-recompose` | loom-ui slice 6a: an agent revision lands while the user types — `renderBlueprintDom`'s `handle.update` reconciles the revised Blueprint by widget id, the focused `<textarea>` keeps text/caret/focus, the kept metric keeps its Lit element and is relabelled through `DomWidgetHandle.patch`, the report is loom's identity report plus `remounted`/`rebound`/`findings`; gap G6 (Blueprint IR 2.4.0, loom ADR 0101 D2): a NEW section inserted ABOVE the one holding the focused, typed-in note is never remounted — same container element, value and focus kept — and container ids share widget ids' one namespace but never collide (`duplicate-node-id`) |
| `experience-kinds` | loom-ui's framework kinds in an unrelated domain (a warehouse board): `Kpi` with a change badge, a columnar `Table` with per-column formats, a `StatusCard` with a polite live region, a localized `Note` via `textProps`, and a dual-axis `TimeSeries` — one Experience compiled for web (Lit, viewer's locale) and terminal (en-US) |
| `experience-layout` | loom-ui placement and section titles (Blueprint IR 2.1.0) in an unrelated domain (a branch-library board): nodes on explicit grid lines (`row` / `rowSpan` / `column` beside `span`), titled sections as `LocalizedText` resolved at compile, `<section aria-label><h2>` on the web and underlined headings in reading order in the terminal, and a revision that moves widgets by restyling them in place; gap G1: `DomRenderOptions.title: "none"` mounts no Blueprint `<h1>` for a host page that renders its own page header, whose mount region is named from it via `aria-labelledby` |
| `experience-stepped` | loom-ui's container-renderer seam (Blueprint IR 2.2.0 `Layout.role`, loom ADR 0099) in an unrelated domain (a bike-share rider onboarding): the app registers its own renderer on `DomRenderOptions.containers` under loom-ui's reference role `"stepper"` (U15; `referenceContainers()` draws it too) — Back/Next chrome and step visibility are the app's, mount/reconcile/subscriptions/focus-pin stay the adapter's; `setRole` toggles chrome in and out with a reported remount, a step title patches the chrome with none, appending a step remounts nothing existing, a throwing renderer falls back to plain, and the terminal prints every step with the role ignored; gap G6: a MID-list step insert shifts every later step's ordinal and still remounts nothing — containers are kept by id (Blueprint IR 2.4.0, loom ADR 0101), never by position |
| `experience-board-edit` | loom-ui operations and planner accounting on a greenhouse board: a widget resized through `setPlacement`, the board titled through `setTitle`, a provider that cannot be retired while bound (nor ever from a widget), the reference planner retiring the provider its own removal orphaned, and `PlanReport.usage` served from the recorded decision on replay; gap G4: a SECOND, multi-step provider (an inlined upstream "station read" step, then the node's own terminal "trend" step) whose tool drifts — `executeProvider`'s `DriftRecord` keys on the TERMINAL step, never `executionGraph[0]`, and the reference planner's `reviseForDrift` repairs it from a sample attached to that step's own tool, leaving the untouched upstream capability's sample alone |
| `split-hydration` | loom-ui split hydration in an unrelated domain (a weather-station board): the browser gets a Blueprint and a handle inventory, never a provider; a `SplitHydrationController` loads through a JSON `HandleLoader`; the server answers with `serveHandle`/`serveHandles` — `$now` tokens on an injected clock, overridable station/time-range params, `Named` reshapers, contract-checked output (an empty alert log is healthy), report-and-proceed for a read-only viewer, and two widgets sharing one upstream reading making exactly ONE upstream call through the batch; gap G3: the browser side imports ONLY the browser-safe `@loom-ui/hydration/client` subpath — bundled with esbuild (platform browser), its graph reaches no `.wasm`, no node builtin and none of the sandbox/MCP/effect-runtime server plane |
| `planner-decide-scope` | A loom-ui `ReferencePlanner` decides THROUGH loom's decide scope (a ticket-triage flow): the model reaches the LLM effect via `scopeInvoker(scope)` (+ per-decider `limitInvoker`/`memoInvoker`), so the call is authorized and observed as the deciding execution — workflowId, executionId and the delegated principal — a flow without the `GrantTable` grant is denied, a resume replays the plan with no model call, and `checkPlannerConformance` passes with a `scopeProbe` over the real runtime; reports two gaps (a denial becomes a durable failed plan; verify cannot see a planner's scope call) |
| `provenance-explain` | loom-ui U12 on an incident-triage board (non-genUI): `plannerProvenance` stamps the recorded decision on the ops, `Lineage.explain` answers "why is this card here" per viewer (a restricted card is bare `{available:false}`, identical to an unknown id; the words are withheld when a classified card raises the class floor), `snapshotSeen` + `SeenLog` record what each viewer was shown (refs sealed under a per-viewer key) and replay "what they saw when they approved" via `read({until})` + `seenToState`, `eraseViewer` crypto-shreds one viewer, `collectSeenGarbage` reclaims their unique blobs while a shared value and the lineage survive, and retention rolls old views off |
| `media-gallery` | Multi-modal media claim-checked by ADDRESS (loom R5 / ADR 0120 + loom-ui U9/U9b): an `agentLoop$` tool declares `returnsMedia` and returns a tiny generated PNG as a ref, a scripted vision model "sees" the resolved bytes (read with `textOf`) while the log holds only addresses; a `ContentResolver(ref, ctx)` authorizes per tenant (denied looks like erased); the provider capability allowlist gives an unknown model id or a custom `baseUrl` a text-only fallback; an `x-content-ref` tool argument (`contentRefArgsFrom(capabilities)` + `acceptContentRefParam`) refuses a ref the caller may not read before the tool runs; a loom-ui gallery of N `Image` widgets bound to MediaRefs with viewer-scoped links; the 64 KiB / 256 KiB inline caps; `sweepUnpinnedContent` pins refs a log cites (and app-table roots) while reclaiming orphans |
| `experience-tabs-planner` | loom-ui U15 (planner depth) on a support-ticket triage view (non-genUI): the `ReferencePlanner` composes ONE nested `tabs` container (Overview / Queue / History) offered through `REFERENCE_CONTAINER_ROLES`, every container stamped `owner: "planner"` and the role rules (2+ titled panels) enforced on the model's reply; `renderBlueprintDom({ containers: referenceContainers() })` draws a real tablist (aria wiring, roving tabindex, keyboard switch keeps focus) while the terminal stacks every panel; a revise is a minimal diff (one `moveNode` + the new tab's inserts, no `revise-recomposed`) and an application-owned container stays locked (`not-owned` / `nested-node`); one `setRole` turns the tabs into a stepper; a panel whose cards are all bound to a `secret` capability collapses to a bare placeholder for a low-clearance viewer (policy A) and `explainNode` answers `{available:false}` |
| `order-lines` | loom-ui's empty binding state (loom ADR 0100, gap G5) on an order-detail board: a DEPENDENT widget ("the top order's lines") whose own step chains off an upstream "top orders" step by a `{{steps.…}}` template; no top order at all indexes past the end of a real (empty) array and the handle publishes `empty` — "No data" on both surfaces (web `role="status"`, terminal's `○ …` row), never an error, never cached, never repaired — while a genuinely bad template KEY, on a non-empty upstream, still errors |
| `incident-shared-chat` | loom R17 shared mode (ADR 0122 D10) on an incident war room: several responders share one conversation, each turn runs AS ITS ASKER (a responder without the grant is `failed / denied`), answers are classified by the tools they touched and filtered per viewer in the history, the SSE stream and the model context (a bare placeholder for whoever is not cleared), turns queue FIFO, every inbox envelope is HMAC-signed (tampered, replayed and stale copies are rejected), a service principal coordinates under an owner-scoped runtime policy asserted at construction, a non-participant is a uniform 404; each viewer's feed is folded by loom-ui `ChatFeed` and printed (one conversation, three transcripts; rejected-on-turn-0 and the `editOfTurn` label). Offline, real SSE transport on port 0 |
