# split-hydration

loom-ui split hydration in an unrelated domain: a weather-station board whose browser never sees a provider.

- **Server** (`src/server.ts`) holds the Experience. `open()` returns the compiled Blueprint and `handleInventory(exp, { revisionOf }).inventory` — per bound handle its priority, the NAMES of its overridable params and an opaque, KEYED revision (`revisionOf` is a fixed demo key here; production uses an HMAC over a server secret, and `handleInventory` throws without one). `hydrate(body)` answers one handle load with `serveHandle`; `hydrateBatch(body)` answers several with `serveHandles` — the endpoint a `HandleLoader.loadMany` posts to. Both resolve relative-time tokens (`$now-24h`) against the server's injected clock, run host `Named` reshapers over the raw tool output, and check each value against its widget kind's contract (`outputCheck: "contract"`).
- **Client** (`src/client.ts`) runs `SplitHydrationController` over a `JsonLoader` (a `HandleLoader`) that crosses a JSON boundary, publishing into its own `HydrationStore`. `loadMany` is required, not optional: the scheduler starts every P0 widget of one bind (and every P1 of one batch window) as a group, and a group leaves as ONE round trip. `setParams({ from, station })` is the time-range picker and station filter: only arguments a step declares `overridable` move.
- **What the tests show** (`test/split-hydration.test.ts`): no provider detail in anything the browser receives; the current-reading and frost-risk widgets both bind the SAME upstream `stations.current` step (each reshaping a DIFFERENT field of its one response — air temperature vs. dew point) and, loading together as one P0 group, make exactly ONE upstream tool call — the batch's step memo, not two; a client's status only ever carries a finding's PUBLIC form (a fixed code and a handle-only message), while the full finding (provider, contract, tool) reaches only the server's own `onFinding` log; an empty alert log is a healthy empty table, not drift; a non-overridable argument (`since`) ignores a param of the same name; a garbled field drifts ONLY the widget that reads it — the sibling widget reading the other field of the same shared reading stays ready, and neither reshaper ever coerces a bad reading into a confident answer; an input-schema drift makes the head stale while a read-only viewer proceeds — both recorded.

Run: `pnpm --filter @loom/split-hydration test`
